# fly living 内容平台设计

- 日期：2026-08-03
- 状态：已完成设计自审，待用户书面审阅
- 项目：`flyoko/fly-blog`
- 目标分支：`setup/personalize`
- 设计基准：70% 内容工作台 + 30% 个人创作空间

## 1. 背景

`fly living` 当前是基于 Nuxt Content 的静态博客。文章以 Markdown 保存在 Git 仓库，站点通过 Cloudflare Pages 部署，正式域名由边缘 Worker 转发，评论服务由独立的 Twikoo 服务和 D1 数据库承载。

现有方式适合工程化维护，但每次新增文章、修改分类或调整模块都需要直接编辑仓库文件。目标是把它扩展成一个仍然以 Git 为内容源、同时具备实时数据能力的个人内容平台，使站长可以通过 `/admin` 完成日常管理，并新增自述、瞬间、AI 阅闻、城市天气和随心听等模块。

本设计不把博客改造成通用低代码平台，也不允许后台注入任意组件或代码。后台只管理已经实现并经过校验的内容类型和模块。

## 2. 已确认的产品决策

1. GitHub 仓库采用单一私有仓库，不拆分公开主题仓库和私有内容仓库。
2. Markdown、站点配置、分类、导航、自述和歌单配置保存在私有 GitHub 仓库。
3. 图片、瞬间附件、音乐封面和音频文件保存在 Cloudflare R2。
4. 瞬间以 Cloudflare D1 为实时主存储，并定期导出到私有 GitHub 备份。
5. 后台完全定制为现有 Nuxt 项目中的 `/admin`，不引入第二套通用 CMS。
6. 后台通过 GitHub 登录，只允许 GitHub 账号 `flyoko` 使用。
7. 普通文章、歌单内容和低风险内容允许直接发布；分类、导航、模块开关、模块顺序、站点设置和数据源配置默认通过分支与 Pull Request 审核。
8. 建设顺序为基础设施优先，其次内容模块，最后统一完成动画和交互优化。
9. 后台视觉采用 70% 工作台 + 30% 创作感：信息架构以长期管理效率为主，欢迎区、渐变、卡片和轻动效负责营造个人创作空间的氛围。
10. `/ai.news` 中原“在花资讯”仅把前台标题改为“站长资讯”，仍使用在花 RSS 数据源，并排在栏目第一位；它与后台人工维护的“站长精选”是两个独立栏目。

## 3. 范围与非目标

### 3.1 本次平台范围

- 私有仓库与自动部署流水线
- GitHub 身份认证和后台会话
- `/admin` 内容管理后台
- GitHub 文件读取、提交、分支和 Pull Request 工作流
- R2 媒体库
- 独立 D1 内容数据库
- 文章、分类、标签、自述、歌单和站点配置管理
- 瞬间实时发布、点赞、评论入口和备份
- `/ai.news` 聚合、缓存、筛选和人工精选
- 城市天气卡片
- 全站音乐播放器
- 统一的浅色、深色和减少动态效果体验
- 发布记录、同步记录、审计日志和故障恢复

### 3.2 非目标

- 多租户或多人协作权限系统
- 任意页面搭建器
- 任意 JavaScript、HTML 或 Vue 组件注入
- 把公开第三方资讯全文镜像到本站
- 抓取或托管未经授权的音乐
- 访客精确定位
- 把 Twikoo 评论数据库与新内容数据库混用
- 首期实现复杂的数据分析、订阅收费或会员体系

## 4. 总体架构

系统分为四层。

### 4.1 公开博客

公开站点继续由 Nuxt 静态构建，保留现有主题的三栏布局和内容表达方式。新增页面与组件如下：

- `/`：文章首页
- `/me`：自述
- `/moments`：瞬间时间线
- `/moments/:id`：单条瞬间详情与稳定评论路径
- `/ai.news`：AI 阅闻
- 右侧栏城市天气卡片
- 全站随心听播放器

文章和自述等 Git 内容在构建时进入静态产物；瞬间、资讯和天气通过同源公开 API 获取。

### 4.2 Nuxt 管理后台

`/admin` 是同一 Nuxt 项目中的独立后台布局。后台静态壳不包含私有内容，登录后再通过 API 获取 GitHub、D1 和 R2 数据。

后台一级导航固定为：

1. 概览
2. 文章
3. 瞬间
4. AI 阅闻
5. 自述
6. 媒体库
7. 随心听
8. 模块管理
9. 发布与审核
10. 站点设置

后台只调用同源 `/api/admin/*`，浏览器中不保存 GitHub、R2 或 Cloudflare 的长期凭据。

### 4.3 Cloudflare API 服务

新增独立 Worker `fly-living-api`，内部按领域拆分路由与服务：

- `auth`：GitHub 登录、会话和退出
- `repo`：读取和写入私有仓库、创建分支和 PR
- `media`：R2 上传、列表、删除和回收站
- `moments`：瞬间、点赞和备份
- `news`：AI HOT、站长资讯和站长精选
- `weather`：城市天气和缓存
- `deployments`：构建、预览和发布状态
- `audit`：审计和同步记录

现有正式域名 Worker `fly-living-edge` 保持站点网关职责：

- 普通页面继续代理到 Pages。
- `/api/*` 通过 Service Binding 转发给 `fly-living-api`。
- API 与后台保持同源，避免跨域和第三方 Cookie 问题。

### 4.4 私有 GitHub 仓库

私有仓库保存：

- Nuxt 源代码
- Markdown 文章
- 自述内容
- 分类和标签配置
- 导航与模块配置
- 歌单配置
- 天气城市配置
- 资讯源配置
- D1 导出备份
- GitHub Actions 工作流

后台的 Git 写操作只针对允许的目录和结构化文件，不提供任意路径编辑能力。

## 5. Cloudflare 资源边界

### 5.1 R2

创建存储桶 `fly-living-media`，绑定自定义媒体域名 `media.flyovo.cc.cd`，关闭生产环境对 `r2.dev` 的依赖。

建议对象前缀：

```text
public/articles/YYYY/MM/
public/moments/YYYY/MM/
public/music/audio/
public/music/covers/
public/profile/
drafts/
trash/
```

规则：

- 发布内容使用稳定 UUID 文件名，避免标题变化导致 URL 变化。
- 上传文件记录原始名称、MIME、大小、哈希、上传者和用途。
- 图片在上传后生成适合正文和缩略图的版本。
- 音频支持 HTTP Range 请求。
- 未被内容引用的 `drafts/` 对象由定时任务清理。
- 删除对象先移动到 `trash/`，保留 30 天后再永久清理。
- 公共文件设置长期缓存；私有草稿只通过短期签名 URL 访问。

### 5.2 新 D1 内容数据库

创建独立数据库 `fly-living-content`。现有 Twikoo D1 保持不变，避免评论系统升级或迁移影响内容平台。

主要表：

- `admin_sessions`：后台会话
- `audit_logs`：后台写操作记录
- `moments`：瞬间正文、状态、地点、标签和关联音乐
- `moment_media`：瞬间与 R2 对象关系
- `moment_likes`：匿名点赞去重
- `news_items`：外部资讯规范化结果
- `news_sources`：运行时数据源状态
- `news_curation`：隐藏、置顶、栏目、点评和人工精选
- `manual_news_cards`：站长手动添加的资讯卡片
- `weather_cache`：最后一次成功天气数据
- `sync_runs`：资讯、天气和备份任务执行记录

所有表使用迁移文件管理，生产更新必须向前兼容，并提供回滚说明。

## 6. 身份认证与权限

### 6.1 GitHub App

采用 GitHub App 完成登录和仓库授权，而不是把个人访问令牌放进前端。

GitHub App 权限限制为目标私有仓库所需的最小范围：

- Contents：读写
- Pull requests：读写
- Metadata：只读
- Actions 或 Checks：只读，用于查看构建结果

登录成功后同时校验 GitHub 用户名和不可变用户 ID，只允许预先配置的 `flyoko` 身份进入后台。

### 6.2 会话

- 浏览器只保存随机会话 ID。
- Cookie 使用 `HttpOnly`、`Secure`、`SameSite=Lax`。
- 会话记录保存在 D1，默认 12 小时过期，活跃时可滚动续期。
- 写操作要求 CSRF Token。
- 登出、密码或 GitHub 授权变化后可撤销全部会话。
- 所有管理员接口再次校验会话，不依赖前端路由守卫作为安全边界。

### 6.3 写入白名单

仓库写入只能落到以下受控区域：

```text
content/posts/
content/about/
content/playlists/
config/site/
config/taxonomy/
config/news/
backups/moments/
```

路径、文件名和数据结构由后端生成并校验。后台不允许传入任意 Git 路径，也不允许提交可执行脚本。

## 7. Git 内容模型

### 7.1 文章

文章继续使用 Nuxt Content Markdown，并保持现有 Frontmatter 能力。后台表单负责生成和校验：

- 标题
- 描述
- 发布日期和更新时间
- 分类
- 标签
- 内容类型
- 封面 URL
- 草稿状态
- SEO 标题和描述
- 固定链接

文章编辑器采用：

- 左侧：文章列表、状态、搜索和筛选
- 中间：Markdown 编辑器与实时预览
- 右侧：元数据、封面、分类、标签、SEO 和发布选项

本地自动草稿只用于防止浏览器意外关闭；正式草稿仍写入私有仓库。

### 7.2 分类、导航和模块配置

现有散落在 TypeScript 配置中的可编辑数据逐步收敛为可校验的 JSON 文件：

```text
config/taxonomy/categories.json
config/taxonomy/tags.json
config/site/navigation.json
config/site/modules.json
config/site/footer.json
config/site/weather.json
config/news/sources.json
```

Nuxt 配置层读取这些文件，并在构建时使用 Zod 校验。这样后台只生成结构化数据，不生成任意 TypeScript 代码。

### 7.3 自述

自述采用独立内容集合：

```text
content/about/profile.md
content/about/timeline.json
content/about/links.json
```

`profile.md` 保存需要富文本表达的简介和自述；时间线、链接和模块顺序使用结构化数据。后台表单可以显示、隐藏和排序预定义模块。

### 7.4 歌单

```text
content/playlists/default.json
```

每首歌包含：

- 唯一 ID
- 标题
- 作者或来源说明
- R2 音频 URL
- R2 封面 URL
- 时长
- 是否启用
- 排序值

首期只支持站长拥有、获授权或可以合法公开播放的音频。不会抓取第三方流媒体的受保护地址。

## 8. 发布策略

### 8.1 直接 Git 发布

以下 Git 内容默认允许直接提交默认分支：

- 新建和修改普通文章
- 新建和修改歌单条目
- 自述正文的普通文字调整
- 文章图片引用变化

直接 Git 发布流程：

```text
后台保存
→ 后端校验内容和目标路径
→ GitHub App 创建 Commit
→ GitHub Actions 执行检查和构建
→ Wrangler 上传到现有 Pages 项目
→ 正式域名继续由边缘 Worker 提供服务
```

提交失败时后台保留未提交内容和最后一次错误，不显示虚假的成功状态。

### 8.2 运行时即时发布

以下低风险运行时数据直接写入 D1，不触发站点重新构建：

- 瞬间的发布、编辑和撤回
- 资讯隐藏、置顶、排序和站长点评
- 人工资讯卡片
- 点赞等轻量互动状态

D1 写入失败时保持前端编辑内容，并且只有在数据库操作成功后才显示发布成功。

### 8.3 Pull Request 发布

以下操作默认创建独立分支和 PR：

- 分类和标签结构变化
- 导航变化
- 模块开关和排序
- 页脚和社交链接
- 自述结构变化
- 天气城市配置
- 资讯源和同步规则
- 其他影响全站的站点设置

PR 流程：

```text
后台修改
→ 创建独立分支
→ 运行 lint、类型检查、静态构建和链接检查
→ 部署 Pages 预览版本
→ 后台展示差异、检查结果和预览入口
→ 管理员确认后合并
→ 生产构建和部署
```

后台不自动合并失败的 PR。

### 8.4 GitHub Actions

生产流水线至少执行：

1. 安装锁定依赖
2. Lint
3. 类型检查
4. Nuxt 静态生成
5. 内部链接检查
6. 部署到现有 `fly-living` Pages 项目
7. 把部署结果回写到 GitHub Check，并供后台查询

PR 流水线执行同样检查，并部署到非生产预览分支。

## 9. 管理后台设计

### 9.1 视觉与布局

后台沿用已确认原型：

- 左侧固定功能导航
- 主区域保持高信息密度
- 顶部欢迎区使用柔和渐变和个人化文案
- 卡片圆角和阴影克制
- 页面切换使用淡入与小幅位移
- 支持浅色、深色和跟随系统
- 支持 `prefers-reduced-motion`
- 移动端降低动画强度

创作氛围只集中在欢迎区、空状态和微交互，不牺牲表格、列表、编辑器和配置页的效率。

### 9.2 概览

概览页展示：

- 写文章、发瞬间、整理阅闻快捷入口
- 文章数、瞬间数、阅闻候选和待审核变更
- 最近编辑内容
- 模块运行状态
- 最近部署、备份和同步状态
- GitHub、R2、D1 或外部数据源异常

### 9.3 媒体库

媒体库支持：

- 拖拽上传
- 文件类型和大小校验
- 图片、音频和其他附件筛选
- 使用位置反向查询
- 复制 URL
- 插入文章或瞬间
- 草稿对象和孤儿文件提示
- 回收站恢复和永久删除

### 9.4 发布与审核

集中展示：

- 直接发布记录
- 待审核 PR
- 检查和构建状态
- Pages 部署状态
- 错误摘要和日志入口
- 重新执行
- 生产版本和回滚入口

## 10. 瞬间

### 10.1 发布流程

```text
后台填写文字
→ 上传或选择 R2 媒体
→ 可关联城市、标签和音乐
→ Worker 校验并写入 D1 事务
→ 前台缓存失效
→ `/moments` 立即可见
```

地点只保存城市级名称和可选国家或地区，不保存精确坐标。

### 10.2 前台

- 时间线分页
- 图片画廊
- 标签和年份筛选
- `/moments/:id` 稳定详情页
- 点赞
- Twikoo 评论入口
- 骨架加载
- 数据错误时展示最后一次成功缓存和清晰提示

点赞使用随机访客 Cookie 的 HMAC 标识进行去重，不保存明文 IP。

### 10.3 备份

每日定时任务导出有变化的瞬间数据：

```text
backups/moments/YYYY/MM/YYYY-MM-DD.json
```

无数据变化时不创建 Commit。备份包含正文、状态、媒体引用、标签和时间，不复制 R2 文件本体。恢复工具可以从指定快照重新写入 D1，并生成恢复审计记录。

## 11. AI 阅闻 `/ai.news`

### 11.1 栏目优先级

前台顺序固定为：

1. 站长资讯
2. AI HOT 实时热点
3. 每日早报
4. 24 小时 / 七日精选
5. 站长精选

“站长资讯”是对在花 RSS 数据源的展示名称调整，不改变数据源。后台和审计日志中保留内部 source key `zaihua`，防止名称变化影响数据兼容。

### 11.2 AI HOT 接入

使用公开 REST API v1 和 ETag 条件请求：

- `/api/v1/hot-topics`
- `/api/v1/items`
- `/api/v1/dailies/latest`
- `/api/v1/selected/snapshot`
- `/api/v1/selected/changes`

不使用已宣布停服的旧 `/api/public/*` 接口。同步任务遵守来源返回的缓存和退避指令。

每条内容保留：

- 标题与摘要
- 分类
- 发布时间和同步时间
- 原始来源
- 原文链接
- AI HOT canonical 链接
- 归属说明

### 11.3 站长资讯

Worker 定时读取在花 RSS，转换为内部 `news_items` 结构。前台只展示标题、摘要、来源、发布时间和原文入口，不复制未经授权的完整正文。

### 11.4 站长精选

站长精选来自两种方式：

- 从已同步资讯中加入精选
- 后台手动创建资讯卡片

后台可以隐藏、置顶、排序和增加简短点评。人工状态保存在 D1，因此调整后无需重新构建站点。

### 11.5 缓存与降级

- Worker 统一请求第三方，浏览器不直连外部数据源。
- 成功响应写入 D1，并使用 Cache API 提供短期边缘缓存。
- 同步失败时继续展示最后一次成功结果，并标明更新时间。
- 连续失败会在后台概览和同步记录中告警。
- 去重优先使用规范化原文 URL，其次使用标题、来源和发布时间指纹。

## 12. 城市天气

后台通过城市搜索选择一个固定城市，不读取访客定位。选择结果保存展示名称、经纬度和时区，前端不自行地理编码。

首个天气适配器使用 Open-Meteo，由 Worker 请求并缓存。页面保留数据来源署名。

天气组件展示：

- 当前温度和天气状态
- 昼夜状态
- 当日最高和最低温度
- 简短生活提示
- 最后更新时间

缓存策略：

- 正常数据缓存 30 分钟。
- 请求失败时可继续使用最近 24 小时内的成功数据。
- 超过降级窗口后显示“天气暂不可用”，不伪造数据。

## 13. 随心听

播放器作为默认布局中的全局组件，由 Pinia 保存状态，在站内页面切换时不中断。

功能：

- 播放和暂停
- 上一首和下一首
- 播放进度和音量
- 顺序和随机模式
- 封面、标题和来源说明
- 展开与收起
- 播放失败自动跳过并提示

浏览器不允许自动播放时，等待用户首次交互。唱片只在实际播放时缓慢旋转；开启减少动态效果后不旋转。

## 14. 公开博客视觉与源码信息处理

公开站点保留主题主体结构，增加统一的柔和背景、卡片层次和轻量动效。

导航：

```text
文章        /
自述        /me
瞬间        /moments
AI 阅闻     /ai.news
友链        /link
归档        /archive
```

默认移除：

- 本站源码入口
- 当前仓库链接
- 原主题仓库链接
- 面向访客无意义的构建版本信息

个人 GitHub 社交链接与源码链接分离，作为独立配置项，默认关闭，可在后台通过 PR 工作流启用。

动效原则：

- 页面切换淡入和小幅位移
- 卡片悬停轻微上浮
- 瞬间时间线顺序显现
- 天气背景随昼夜变化
- 唱片仅播放时旋转
- 加载、保存、错误和完成状态都有明确反馈
- 不使用影响阅读的持续大幅动画

## 15. 错误处理与可恢复性

### 15.1 GitHub

- Commit 或 PR 创建失败时保留编辑内容。
- 发生 SHA 冲突时提示重新拉取差异，不覆盖远端内容。
- 构建失败时保持当前生产版本在线。
- 每次发布保留 Commit、PR、构建和部署关联 ID。

### 15.2 R2

- 上传失败可重试，不清空编辑器。
- 多文件上传逐项报告结果。
- 删除先进入回收站。
- 内容发布前检查所有引用对象是否存在。

### 15.3 D1

- 瞬间发布使用事务写入正文和媒体关系。
- API 只有在事务成功后返回发布成功。
- 数据库迁移在预览环境验证后再进入生产。
- 每日备份支持指定快照恢复。

### 15.4 外部数据源

- AI HOT、站长资讯和天气均保存最后一次成功结果。
- 请求使用超时、指数退避和最大重试次数。
- 失败不清空现有数据。
- 后台显示来源级健康状态和最近错误。

## 16. 安全与隐私

- 所有密钥仅存 Cloudflare Secrets 或 GitHub Actions Secrets。
- GitHub App 安装范围限制到单个私有仓库。
- 后台写接口进行身份、CSRF、数据结构和路径四层校验。
- 管理接口和上传接口增加频率限制。
- 上传校验 MIME、扩展名、文件大小和文件签名。
- 富文本渲染执行 XSS 清理。
- 外部 URL 仅允许 `http` 和 `https`，并阻止内网 SSRF 地址。
- 审计日志记录操作者、操作类型、目标、结果和时间，不记录 Secret。
- 瞬间地点只保存城市级信息。
- 匿名点赞不保存明文 IP。
- 公开媒体可被访问者下载；私有仓库和 R2 分离只能防止 Fork 同步，不承诺阻止公开内容被保存。

## 17. 性能与可访问性

- 公开页面优先静态生成。
- 瞬间、资讯和天气 API 使用边缘缓存。
- 图片使用响应式尺寸、现代格式和懒加载。
- 首屏不加载未展开播放器的大尺寸封面或全部歌单。
- 动画只使用 `transform` 和 `opacity` 等低成本属性。
- 支持键盘导航、可见焦点和语义化标签。
- 颜色对比满足常用无障碍标准。
- 完整支持 `prefers-reduced-motion`。
- 移动端隐藏次要侧栏，并把天气和播放器移动到正文后方或底部浮层。

## 19. 分阶段交付

本项目由多个独立子系统组成，不在一个实现周期中同时落地。此文档是总设计，后续每个周期单独编写验收标准和实施计划。

### 周期 1：基础设施与后台骨架

- 将仓库调整为私有
- GitHub App 和只允许 `flyoko` 的登录
- `fly-living-api` Worker 与同源 API 路由
- `fly-living-content` D1 和初始迁移
- `fly-living-media` R2 与媒体域名
- GitHub Actions 生产和 PR 流水线
- `/admin` 视觉骨架和导航
- 媒体库基础能力
- 文章读取、编辑、直接发布和 PR 发布
- 发布状态、审计和错误提示

### 周期 2：自述与瞬间

- 自述内容模型和后台表单
- `/me`
- 瞬间 D1 模型和后台
- `/moments` 与详情页
- R2 图片、点赞、Twikoo 评论入口
- D1 到 GitHub 定时备份和恢复

### 周期 3：阅闻、天气与随心听

- AI HOT v1 聚合
- 站长资讯 RSS
- 站长精选和人工卡片

### 周期 4：统一视觉、动效与优化

下一步只为“周期 1：基础设施与后台骨架”编写验收标准和实施计划。后续周期在前一周期验收后分别进入新的设计确认和计划流程。

## 20. 运维与部署约束

- 继续使用现有 Pages 项目和正式域名，不为了接入 GitHub 重新创建站点。
- 私有仓库通过 GitHub Actions 使用 Wrangler Direct Upload 部署。
- 正式域名 Worker 的现有代理行为必须保持兼容。
- Twikoo 服务和现有 D1 不在周期 1 中迁移。
- 生产 Secret 不写入仓库、构建日志或浏览器。
- 开发执行期间不得重新克隆或覆盖当前仓库。
- 设计文档、验收标准和实施计划在用户明确授权前不提交或推送 Git；产品后台未来产生的内容 Commit 属于系统功能，不等同于开发过程授权。

## 21. 成功标准

完成全部周期后，站长应能：

1. 通过 GitHub 身份安全进入 `/admin`。
2. 不打开代码编辑器即可创建、修改和发布文章。
3. 通过受控 PR 修改分类、导航、模块和站点设置。
4. 把媒体上传到 R2，并在文章、瞬间和歌单中复用。
5. 发布瞬间后立即在前台看到，并能从 Git 备份恢复。
6. 在 `/ai.news` 首先查看“站长资讯”，并使用 AI HOT、日报和站长精选。
7. 通过后台配置天气城市和随心听歌单。
8. 在桌面和移动端获得一致、舒适且不过度的视觉和动效体验。
9. 在外部 API、构建或上传失败时看到可理解的错误，并能重试或恢复。
10. 让源码、未发布内容、配置和历史提交保持在私有仓库中，同时公开站点继续稳定访问。

## 22. 外部接口依据

- AI HOT：使用公开 REST API v1、RSS 与 ETag 机制，保留来源和原文入口。
- 站长资讯：使用 `https://www.zaihua.news/rss.xml`，仅改变本站展示标题。
- 天气：首个适配器使用 Open-Meteo，保留其要求的数据来源署名。

这些外部依赖全部通过 Worker 适配器隔离。来源接口字段或策略变化时，只替换对应适配器，不让 Nuxt 页面直接依赖第三方响应结构。
