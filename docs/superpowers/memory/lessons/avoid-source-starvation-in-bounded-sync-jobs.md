# 避免有界同步任务中的来源饿死

## 问题特征

一个同步轮次按优先级串行处理多个来源，并为可选的图片抓取设置了总时间预算。高优先级来源能够正常写入图片，但后续来源虽然显示同步成功，图片却长期保持为空。

只检查整轮状态或成功率会掩盖问题：来源请求、正文更新和状态写入都可能成功，真正被跳过的只是预算耗尽后的可选增强步骤。

## 非显然根因

全局 deadline 同时承担了“防止单次同步失控”和“限制每个来源资源消耗”两个职责。前一个来源消耗完 deadline 后，后续来源继承的是已经过期的预算，因此会稳定饿死，而不是偶发超时。

来源优先级不应该隐式决定可选增强能力是否永远可用。

## 可执行规则

1. 把预算放在需要公平隔离的边界上。多个独立来源共享调度循环时，默认使用“每来源预算”，并在 `finally` 中清理状态。
2. 在预算内继续保留更细粒度限制，例如每文档预算、单请求超时、并发数和字节上限。
3. 可选增强失败时保留已经验证过的正文和历史资源，不得把空结果覆盖到已持久化数据。
4. 生产验收必须按来源统计增强结果，不能只看整轮成功状态或聚合总数。
5. 回归测试要让前一来源明确耗尽预算，再断言后一来源仍能完成增强，避免普通成功路径掩盖公平性问题。

## 诊断步骤

- 比较各来源 `last_success_at` 与增强字段的非空数量。
- 确认成功状态是否只代表主同步流程，而不代表图片等可选步骤完成。
- 搜索跨来源共享的 deadline、计数器、信号量或 mutable state。
- 用逻辑时钟或可控延迟复现前一来源耗尽预算的场景。
- 修复后同时验证前后来源，不能只验证最先执行的来源。

## 不适用场景

- 多个步骤共同组成一个不可分割事务，任何一步超时都应中止整轮时，不应强行拆分预算。
- 下游有严格的整轮执行时限时，可以保留全局硬上限，但仍需在其内部做公平分片、轮转或配额，不能让固定优先级来源永久占满预算。

## 证据

提交 `70e822ca3bf9d7fd1b3a0da576bd65788d74cdc8` 将图片同步预算从整轮共享改为每来源隔离，并增加了“前一来源耗尽预算、后一来源仍成功落图”的回归测试。生产验证中 AI HOT 图片文档从 0 增加到 2，证明后续来源不再被站长资讯饿死。
