# 静态内容的草稿保护必须同时覆盖入库与查询

## 问题特征

文章在首页和详情查询中已经过滤了 `draft: true`，浏览器页面也看不到草稿，但静态构建产物仍可能包含草稿标题、正文或元数据。常见泄露入口包括 Nuxt Content 的公开数据库、原始内容接口、Atom、站点统计、相邻文章和直接路径。

只验证页面 DOM 或列表结果会漏掉这一类问题，因为静态站点会把内容索引作为可下载资源发布，访问者可以绕过页面查询直接读取构建数据。

## 非显然根因

运行时 `.where('draft', '=', false)` 只约束某一次查询，不会阻止构建器先把草稿写入公开 Content 数据库。详情、列表、订阅和统计又通常各自维护查询，任何一个遗漏都会形成独立泄露面。

草稿保护因此不是单一页面权限判断，而是两层边界：

1. 构建入库边界决定敏感内容是否进入公开产物。
2. 所有公开读取边界决定已入库内容是否出现在页面和衍生输出。

## 可执行规则

1. 静态内容源在构建入库前排除显式草稿文件，不能只依赖页面查询过滤。
2. 公开文章索引、详情、相邻文章、订阅源、统计和搜索分别显式添加 `draft = false`，不要假设共享调用链会自动继承。
3. 草稿识别只读取 frontmatter 顶层的显式 `draft: true`，不得把嵌套对象中的同名字段误判为整篇草稿。
4. 查询结果允许为空时，分类和排序组合函数必须把 `null` / `undefined` 归一化为空数组，避免草稿被全部排除后构建崩溃。
5. 发布验收必须扫描公开 HTML、Atom、统计 JSON 和 Content 数据库，并直接请求已知草稿路径确认 404。
6. 回归测试同时覆盖查询契约和构建产物；仅有组件测试或页面截图不足以证明没有泄露。

## 诊断步骤

- 在生成目录中搜索一篇已知草稿的唯一标题和正文片段。
- 检查 Content SQL dump 或数据包是否仍含草稿行。
- 枚举所有 `queryCollection`、相邻文章、feed 和统计调用，确认每个公开入口都有过滤条件。
- 直接请求草稿 URL、原始内容 URL、payload 和数据文件，不能只从导航进入。
- 暂时让全部文章均为草稿，确认归档、分类和排序仍能以空集合完成构建。

## 不适用场景

- 需要登录后在线预览草稿时，应使用独立的受鉴权服务或私有数据源，不要把草稿继续放进匿名可下载的静态数据库。
- 纯服务端、数据库本身不可公开访问的应用可以只在统一授权查询层控制，但仍应避免多个公开读取点各自复制权限逻辑。
