# 公开资源 URL 必须按浏览器规范化语义校验

## 问题特征

后台配置允许 HTTP(S) 地址和以单斜杠开头的站内路径，字符串校验看似已经拒绝 `//evil.example`，但某些输入仍会在浏览器中变成跨域链接。例如 `/\evil.example/path` 会被 URL 解析器规范化为 `https://evil.example/path`。

如果渲染层仍把这类值当成站内链接，就会绕过外链标识、`target`、`rel` 或域名策略。

## 非显然根因

URL 校验只检查了字符串前缀，没有先考虑浏览器对反斜杠和控制字符的规范化行为。WHATWG URL 解析会把部分反斜杠视为路径分隔符，并忽略换行、回车或制表符，因此“原字符串不像外链”不代表“最终导航目标仍在本站”。

## 可执行规则

1. 对允许公开展示的链接和图片地址，先拒绝反斜杠、C0 控制字符和 DEL，再判断相对路径或绝对 URL。
2. 站内路径只允许单个正斜杠开头，并显式拒绝 `//`；绝对地址只允许 `http:` 和 `https:`。
3. 安全测试要使用 `new URL(candidate, trustedOrigin)` 检查浏览器最终解析结果，不能只断言字符串正则。
4. 链接的外部/内部分类、`target` 和 `rel` 必须建立在已经通过 schema 的值上，不能让未校验配置直接进入组件。
5. 配置发布 API 与前台构建必须复用同一个 schema，避免后台接受、前台误判或反过来的契约漂移。

## 诊断步骤

- 用可信 origin 分别解析 `/safe/path`、`//evil.example`、`/\evil.example` 和含换行的变体，比较最终 origin。
- 检查 schema 是否只验证前缀，或是否允许浏览器会忽略/重写的字符。
- 核对前台外链判断是否处理的是原始值、trim 后值还是 URL 规范化结果。
- 在 Worker 发布契约和前台组件测试中加入同一组恶意边界样例。

## 不适用场景

- 值永远不会进入浏览器 URL 上下文时，不需要套用导航地址规则，但仍应按其实际语法上下文进行输入验证。
- 需要支持协议相对 URL 时，应明确列出允许域名并在解析后校验 origin，不能简单放开 `//`。
